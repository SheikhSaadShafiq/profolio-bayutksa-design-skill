Handover — running this on your own machine

Everything this project knows is in two repositories and one rule: no value is written that was not measured from a render. Since 2026-09-28 that rule is kept the strict way: the pages are no longer written from measurements at all — they are compiled from the product's own render, and the design system is cut out of them. Every page, state and component carries the score it got against the product it came from.

The two repositories

repowhat it is
chaudhary-umair-ahmad/profolio-bayutksa-design-skill This one. The design system, the compiled pages, the knowledge base and all the tooling. The compile work is on branch pixel-perfect (local).
SectorLabs/profolio-reactjs The product. Read, never modified — except for the dev-only /design-capture route, kept here as product-route/design-capture.patch. The pass of 2026-09-28 was compiled from a copy of it dated that day (Profolio-Surge-28sep), put under a local git so every harness change to it is visible.

They must sit side by side: every script defaults to ../profolio-reactjs (a symlink is fine) and the harness reads PROFOLIO_REPO if you keep it elsewhere.

Setting up on a Mac

# the product: its own install, with the Nexus credentials in its .npmrc
cd ../profolio-reactjs
git apply ../profolio-bayutksa-design-skill/product-route/design-capture.patch
yarn install

# this repo
cd ../profolio-bayutksa-design-skill
npm install
npx playwright install chromium
npm run all

The harness runs its own dev server on port 3100, with harness/env passed as process environment (which Vite ranks above every .env file) and its own dependency cache (harness/vite.config.mjs, copied into the product untracked). So someone's normal yarn start on 3000, signed in to staging with a staging .env, keeps running beside it and is never touched. Do not run harness/install.mjs against a real install — it was for a sandbox with no Nexus access and rewrites .env and the lockfile.

What is built

  • deliverables/design-system.html — foundations measured from what the compiled pages paint (Figtree and Droid Arabic Kufi, the colour ramps, the type scale, the corners), every component as atom, molecule, organism or template (antd's, as the product themes them, and the product's own, named and sourced from its files), every page and state, and the product knowledge that goes with them.
  • deliverables/components/ — a page per component: live variants, markup, exact CSS, forced hover/focus/active, anatomy, usage, source, copy; a spec sheet per variant (measured, with its token names) and, for buttons, inputs, selects, pickers, checkboxes, radios and switches, a table of every state — seen, forced or derived.
  • deliverables/<page>.html and deliverables/states/ — the 24 pages and every state, compiled: overlays and what they lead to (--<parent>__<child>), form states (errors, filled, saved, failed), --loading / --empty / --error on every signed-in page, four flows as numbered steps (--flow-<flow>-<nn>-<step>: post a listing, ad licence, buy a package, top up credits), and the account variants (--as-staff and --as-individual on every signed-in page, --profile-incomplete, --modal-non-saudi). A clickable prototype: a trigger opens its state; Escape, ✕, Cancel or the mask go back to where it was opened from; ← and → walk a flow; the rail and menus go to the other pages; M opens the same screen in the other layout.
  • deliverables/mobile/ — the responsive layout: the same pages and states as the product draws them for a phone (375, mobile user agent — the product picks its phone layout by device, src/utility/general.js).
  • deliverables/responsive.html — the responsive rules, counted from both layouts: which overlays become drawers, which components change size, what only one layout has, screen by screen.
  • deliverables/design-qa.html — every page, state and component held to the product's render, the live product on two real accounts, and the code.
  • kb/screens/ and data/design-kb.json — the design knowledge base: every screen and state, web and responsive, in words — what it is for, how it is reached, what it shows, the components it adds, the file to open — searched by scripts/design-find.mjs.
  • deliverables/profolio.css (the product's CSS, renamed: ant-* → pf-*, styled-components → the JSX name the product wrote) and tokens.css (the named values).
  • harness/fixtures/ — the invented account, one module per area, answering every endpoint in the real API's shape for two real accounts: an agency owner (data/api-shapes.json) and an agency staff user (data/api-shapes.b.json, fixture mode staff) — recorded from signed-in sessions as keys and types only. The individual seller (individual) is the owner's record with the agency taken away, not a recording. Modes: accounts (staff, individual, incomplete, non-saudi, member, projects), data (slow, error, empty), forms (form-fail, lead-duplicate, photo-rejected, preferences-flipped, …), payments (pay-*: a package, an ad licence, declined, cancelled, Tabby refused, Nafath pending, …) and the listing form (lf-*: Nafath, too few credits, a failed upload).

Known gaps

  1. English only; web at 1440 and the phone layout at 375. Arabic RTL and tablet widths were out of scope; the harness can capture --rtl and the compiler would follow.
  2. The product is wider than a phone. At 375 its content overflows to about 433px (deliverables/design-qa.html lists where); the compiled pages reproduce it, as they reproduce everything.
  3. /user-settings/preferences crashes for any account without a photo — a product bug at common/transformers/user.js:35. The harness compiles it on an image record whose sizes are empty, which renders the same.
  4. The phone's FEEDBACK tab covers the right edge of most pages and takes any tap there (deliverables/design-qa.html); a state whose control sits under it is reached by tapping the part a person can see.
  5. A few component cut-outs differ from their in-page shot — small icons and tags where a composited layer snaps to whole pixels. Each says so on its own page.

Gotchas that cost real time

  • Two Vite servers sharing node_modules/.vite re-optimise under each other when their defines differ. The harness has its own cache dir.
  • A browser with classic scrollbars lays a 1440 viewport out at 1425. Headless Chromium has none. Hide the scrollbar before capturing a signed-in page, or every width is 15px off.
  • A styled-components componentId sits on every variant. Renaming it to variant 1's name makes variant 1's rules land on all of them — a column Flex on every row. The compiler drops it unless a rule selects it.
  • A span in a flex row is blockified. Cut out of the row it is inline again and ignores its width; a cut-out keeps its computed display.
  • Forced-state CSS must copy only the selector parts that had the pseudo-class, or the plain parts are re-applied after the whole stylesheet and win.
  • A fixture in last year's shape does not fail — the product renders blanks. "for undefined" on every Credits card was a renamed field. check-fixtures exists for that.
  • First-visit UI hides the page: the LMS tours and the "Profile Completed" modal. The harness dismisses them the way a returning user has them, and states bring them back (harness/page.mjs).
  • Never read canvas/*.dc.html into an agent's context.
  • The viewport meta is part of the layout. Compiled pages carried a generic one; without the product's maximum-scale=1.0, user-scalable=0 a phone widens its layout viewport to the product's overflow, and every fixed bar with it. A full-page screenshot hides this — it resizes the viewport anyway. Compile copies the product's.
  • A link inside a link does not survive HTML. React builds it; the parser closes the outer link at the inner one, and the phone's app banner lost its text column. Such links are written <pf-nested-a> and made real by a line of script (scripts/lib/nested-a.mjs).
  • A failed state can poison the next. A state that sets a harness flag and times out leaves it set; compile clears every pf-harness-* flag before each state.
  • clientWidth is rounded. Centred text in a 72.39px box is not centred in 72px — widths come from the rect. And an inline box takes no vertical margin, so an inline cut-out is placed by the box around it.
  • Mobile emulation is not a phone-width window. Collect the responsive components in a plain 375 window — exactly what a component page's frame is — or shots of anything in the overflow come out blank.
